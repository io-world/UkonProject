Research agents: from one practice to every renewal

For the prototype I researched one real business by hand: its legal entity, its web and email footprint, and the recent incidents in its industry. This page describes how that becomes a set of AI agents that does the same for every client an agency renews, which steps the model does, which steps are plain code, and where a person stays in the loop.

The core idea: two jobs, run on different clocks

The research splits cleanly into work that is specific to one business and work that is shared by every business in an industry. Keeping them apart is what makes it cheap at scale.

Per client · at each renewal

Client profile

Who exactly is this business, what does it do, how big is it, what does it expose to the internet, which vendors hold its data? Runs 90–120 days before renewal and refreshes only what changed the next year.

Per industry · on a schedule

Industry threat file

What is actually happening to businesses like this one: breaches, ransomware, vendor incidents, regulation. Runs weekly per industry code. One dental file serves every dental client; only a one-line tailoring step is per client.

A thousand dental practices need one dental threat file plus a thousand cheap client profiles, not a thousand research projects.

The client agents

They run in order for each renewing client. Each one writes its output to the wiki (evidence) and the database (values), so the next agent and any person can see exactly what it did.

AGENT 1 Entity resolver

Turns "the account the agency calls Sloan's Lake Dental" into one legal entity that can be the named insured.

Input
Account name, mailing address, contact email domain from the agency system.
Tools
State business-registry adapters; industry registries (NPI for healthcare, licensing boards for trades, FINRA for advisors); web search on the trade name.
Does
Searches wide (legal names, trade names, "doing business as" records), then scores every candidate on name, address, state, domain and registry status together. A delinquent or dissolved entity is down-weighted even if name and address match exactly.
Output
A ranked candidate list, each with the signals that matched and its source record.
Human
Always confirms Quoting the wrong company is the worst failure in the whole process.
Model's job
Generating search variants and reading messy registry pages. The score itself is code.

AGENT 2 Footprint collector

Gathers everything public about the confirmed business, and saves it before anyone reads it.

Input
The confirmed entity and its domain.
Tools
Fetcher (website pages: home, team, services, privacy policy), public DNS lookups (mail provider, sender policy, DMARC), directory and review sites, press releases, job postings.
Does
Decides which pages are worth fetching, follows only same-business links, and saves each fetch as an immutable raw source with its URL and retrieval date.
Output
A folder of raw sources per client, e.g. wiki/raw/sloanslake/website.md, dns_records.md.
Human
None at this step.
Model's job
Choosing what to fetch and recognizing irrelevant or wrong-business pages. DNS lookups are plain code.

AGENT 3 Signal extractor

Reads the raw sources into structured facts. The only step where the model interprets content.

Input
The client's raw sources.
Does
Pulls headcount signals, number of providers, services, online payments, vendors that hold data, data sensitivity, owner name, location. Every value carries the source file and the line it came from; conflicting values are kept side by side, not averaged.
Output
One signals record per client (signals.md), e.g. "3 dentists (team page, Oct 2026); WebMD lists 7 (stale)".
Human
None directly; conflicts surface at review.
Guardrail
Sources are data, never instructions: a web page that says "ignore previous instructions" is just text in a file.

AGENT 4 Verifier (critic)

A second model that checks the profile instead of building it, the same proposer/critic pattern used for QA pipelines.

Input
Signals, estimates and the raw sources behind them.
Does
Checks that every claim cites a source, that cited text actually says it, that sources agree, and that nothing is stale (older than 24 months) or from the wrong entity. It flags; it never edits a value.
Output
Flags on fields ("needs review") with a plain reason.
Human
Reads the flags at review.

NOT AN AGENT Estimators (plain code)

Revenue, headcount and the exposure score are computed, not generated. Revenue uses a waterfall: the agency's own record, then a public filing, then two independent benchmark methods (staff × revenue per employee; providers × billings per provider). Each estimate has a range, a confidence and a written method. When nothing public gives a number, the estimator says so and flags it, as it did for Sloan's Lake's headcount. Keeping this out of the model means every number is reproducible and auditable.

The industry agents

They run on a schedule per industry code (and region), independent of any client. Their output is a shared, approved library.

AGENT 5 Industry researcher

Runs
Weekly per industry code, plus regional queries ("dental ransomware Colorado") and vendor queries for vendors that show up in client profiles (booking, payments, email, IT providers).
Sources
Trade press, the HHS breach portal for health, state attorney-general notices, regulator enforcement pages, security vendors' reports, ransomware leak trackers.
Output
Candidate items, each fetched and saved.

AGENT 6 Research verifier

Checks
URL is live; dated; named source; every figure in the summary appears in the source; duplicates merged; leak-site postings labeled "claimed", not "confirmed".
Expires
Items older than about 18 months leave the client pack but stay in the library.
Human
CPL approves before an item can reach any client.

AGENT 7 Tailor

Runs
When a client pack or agent brief is built.
Does
Picks the approved items most relevant to this client and writes one line linking each to the client's own facts, e.g. a DMARC study linked to "your domain has no DMARC record".
Rule
May not introduce a number; figures come only from the cited source or the database.

Also: the refresher

Between renewals, a light monitor re-checks a few cheap signals for every client and opens a follow-up when one changes: registry status (an entity goes delinquent), a new incident at a vendor the client uses, a DMARC record appearing. Next year's renewal starts from the existing wiki and re-fetches only what changed, so each client's file compounds instead of starting over.

Source adapters: the real moat

The model never "browses for the legal name". It calls adapters with known shapes and reads what they return. Building and maintaining these is most of the engineering work, and the part that is hardest to copy.

Confidence and review: who looks at what

High

An official record, or the agency's own rating data, under 12 months old. Passes without review.

Medium

Two or more independent sources agree within ±20%. Passes; visible on hover.

Low

One source, an old source, sources that disagree, or an estimate built on an assumption. Goes to a person.

Two items always go to a person regardless of confidence: the entity match, and any estimated revenue. Every human change is logged with who, why and where the new value came from; over time those overrides are labeled data that show where the agents are weakest.

Guardrails

Evidence before claims

Every fetch is saved before it is read. Every fact cites a saved file. If it isn't in the wiki, it didn't happen.

Numbers never come from the model

Figures come from a source (quoted) or the estimators (computed). Generated prose uses placeholders, and any digit in it fails validation.

Sources are data, not instructions

Web content can carry prompt injection. Agents read it as quoted material in a fixed extraction format and cannot act on it.

Business data, not personal data

An owner's name in a federal registry is fair game; a home address or personal social media is not. Respect robots rules, site terms and rate limits.

An estimate is not a security rating

The exposure score is labeled as a rough proxy from public signals. It is never presented as a scan or an assessment of the client's security.

Coverage questions escalate

No agent answers "would this be covered?". Those go to a Cyber Practice Leader, always.

Worked example: what the agents would have done for Sloan's Lake Dental

This is the research I did by hand for the prototype, written as the agents' steps. Everything here is real public data, retrieved October 2026.

  1. Entity resolver: searched the Colorado registry for "Sloan* Dental" and "Sage Dentist*". Found Sage Dentistry, PLLC in good standing at 2750 W 29th Ave, a Sloans Lake Dental PLLC at the same address but delinquent since May 2022, six dissolved "Sage Dentistry II–VII" offices, an unrelated 2005 entity, and a look-alike (Sloanside Dental) in Edgewater. The NPI organization record tied the trade name to Sage Dentistry, PLLC. Ranked: 100% vs 37% for the delinquent one. Person confirms
  2. Footprint collector: saved the website (3 dentists, implant and cosmetic services, online booking and bill pay through a vendor, a marketing firm running the site), public DNS (encrypted email service, Microsoft 365, strict sender policy, no DMARC record), two directory listings (one at a stale second address), and two press releases.
  3. Signal extractor: 3 dentists (team page and press release agree; a directory's 7 is stale), online payments yes, patient health data yes, vendors listed with their roles. No published headcount or revenue.
  4. Estimators: headcount 12 (assumption, low confidence); revenue $2.35M with a $1.65M–$3.2M range from two methods that disagree by ~$1.1M, so low confidence; exposure 68/100 from public signals.
  5. Verifier: flagged revenue and headcount (estimated), noted the stale directory address and dentist count as ignored conflicts.
  6. Industry researcher + verifier: a Longmont, Colorado dental breach (3,735 people, reported Oct 2026), a ransomware group listing a Colorado dental practice (a claim, labeled as such), a 2026 report that most breached healthcare organizations lacked DMARC enforcement, phished staff mailboxes behind several 2026 dental breaches, and a settlement after attackers entered through a dental group's IT provider.
  7. Tailor: linked the DMARC report to this practice's missing DMARC record and its encrypted-email setup; linked the vendor incidents to its booking and payment vendor.

Measuring it

MetricWhat it tells you

Time and cost per profileModel calls, fetches and paid data per client; what the agency would otherwise spend in staff minutes.
Profiles that reach "indication-ready"The business outcome: clients whose renewal now includes a cyber option.

Where it breaks

Common names

"Smith Dental" returns dozens of candidates. Without an address or domain from the agency, the resolver must stop and ask rather than guess.

Coverage gaps

States without open registries; very small businesses with no website; sole proprietors with no entity at all.

Stale third parties

Directories keep old addresses and old staff, as with Sloan's Lake's second listing. Official records win every tie.

Revenue for private firms

Rarely public. Benchmarks give a range, not an answer, which is why estimated revenue always goes to a person and is confirmed with the client.

Build order

First

One industry, one region: dental in Colorado. The entity resolver with the state registry and NPI adapters, the footprint collector, the estimators, review by exception. Measure the override rate on real renewals.

Next

The industry researcher and verifier with a CPL-approved dental library; the tailor; the refresher. Add the next two industries by renewal volume.

Later

More state adapters (or a commercial aggregator), vendor-incident monitoring across all clients, and using override data to tune the confidence rules per industry.
